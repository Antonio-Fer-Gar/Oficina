# OMP live agent observability and intervention

## Bottom line

OMP has real lifecycle and control surfaces, but they are scoped to a live OMP process/session; the session JSONL transcript is not an IPC command channel.

- A startup-loaded extension can observe its bound session and the task/subagent event bus. Because task child sessions rebind the extension to their own session context, a deliberately preloaded extension can also implement a **custom, targeted local bridge** that routes a command to a child instance and then calls that instance's public `sendUserMessage`, `setModel`, or `abort` action. This is not a built-in parent-to-child extension command API, and it requires the bridge code to already be loaded in the running process.
- For already-running interactive sessions, Collab is the documented external attach/control surface **only when the session is already hosting Collab**. Its local registry enumerates those hosts, and a full-control guest can observe/control subagents and answer supported UI prompts. The local read-only discovery found `hosts: []`; no currently discoverable Collab session was available. See [local environment check](./omp-local-smoke.md).
- RPC is a good host-owned process protocol, not an attach-to-TUI protocol: the host starts `omp --mode rpc` and sends commands over that process's stdin. RPC exposes parent-session state and subagent commands when enabled, but no command attaches to an arbitrary already-running interactive process.

Scope: upstream references below are pinned to `v18.13.2`, matching the local executable version reported by the parent session; `omp.sh` documentation is live and may move ahead of that tag. No user credentials, configuration, or session transcripts were inspected.

## What can be observed

### Extension events, including subagent work

The public extension API has typed `pi.on(...)` lifecycle handlers, including `agent_start/end`, `turn_start/end`, message and tool-execution events, and `tool_approval_requested` / `tool_approval_resolved`. Approval requests carry `sessionId`, `toolCallId`, `toolName`, optional `reason`, and `approvalMode`; resolutions carry the same identifiers plus `approved` and optional `reason`. See [`ExtensionAPI.on` and event payloads](https://github.com/can1357/oh-my-pi/blob/v18.13.2/packages/coding-agent/src/extensibility/extensions/types.ts#L1295-L1312) and [handler overloads](https://github.com/can1357/oh-my-pi/blob/v18.13.2/packages/coding-agent/src/extensibility/extensions/types.ts#L1788-L1793).

Task children additionally publish these source-defined generic EventBus channels:

- `task:subagent:lifecycle`: `{ id, agent, agentSource, description?, status: "started" | "completed" | "failed" | "aborted", sessionFile?, parentToolCallId?, index, detached? }`.
- `task:subagent:progress`: `{ index, agent, agentSource, task, parentToolCallId?, assignment?, progress, sessionFile?, detached? }`.
- `task:subagent:event`: `{ id, event }`, where `event` is an `AgentSessionEvent`.

The channel constants and event payload are in [`task/types.ts`](https://github.com/can1357/oh-my-pi/blob/v18.13.2/packages/coding-agent/src/task/types.ts#L31-L40); lifecycle/progress payloads are in [`session-observer-registry.ts`](https://github.com/can1357/oh-my-pi/blob/v18.13.2/packages/tui/src/overlays/session-observer-registry.ts#L1-L38). Progress includes task status (`pending`, `running`, `completed`, `failed`, `aborted`), current tool/arguments/intent, retry state, counters, and model routing (`modelRole`, `resolvedModel`, thinking level, fallback flag) in [`AgentProgress`](https://github.com/can1357/oh-my-pi/blob/v18.13.2/packages/tui/src/tools/task.ts#L2337-L2393).

`ExtensionAPI.events` is a generic `EventBus` with `on(channel, ...)` and `emit(channel, ...)`, distinct from the typed `pi.on` catalog ([API member](https://github.com/can1357/oh-my-pi/blob/v18.13.2/packages/coding-agent/src/extensibility/extensions/types.ts#L2043-L2044); [implementation](https://github.com/can1357/oh-my-pi/blob/v18.13.2/packages/coding-agent/src/utils/event-bus.ts)). In `sdk.ts`, the same session `eventBus` is passed both when binding extensions and into the tool session; `structured-subagent.ts` forwards `session.eventBus` into child launches, and the task executor emits the task channels there ([bus setup/binding](https://github.com/can1357/oh-my-pi/blob/v18.13.2/packages/coding-agent/src/sdk.ts#L1785-L1787), [tool and extension binding](https://github.com/can1357/oh-my-pi/blob/v18.13.2/packages/coding-agent/src/sdk.ts#L2444-L2446), [child inheritance](https://github.com/can1357/oh-my-pi/blob/v18.13.2/packages/coding-agent/src/task/structured-subagent.ts#L641-L644), [progress emission](https://github.com/can1357/oh-my-pi/blob/v18.13.2/packages/coding-agent/src/task/executor.ts#L1629-L1635), [raw child event emission](https://github.com/can1357/oh-my-pi/blob/v18.13.2/packages/coding-agent/src/task/executor.ts#L1734-L1735), [lifecycle emission](https://github.com/can1357/oh-my-pi/blob/v18.13.2/packages/coding-agent/src/task/executor.ts#L2987-L2988)). Therefore a root extension listener can observe task descendants, and child-bound instances can publish their own events on that shared bus.

**Identity and coverage gaps:** `ExtensionContext.agent` has `kind`, `id`, `name`, `depth`, and `parentId`; `ctx.cwd` and `ctx.model` are for that bound session ([identity](https://github.com/can1357/oh-my-pi/blob/v18.13.2/packages/coding-agent/src/extensibility/extensions/types.ts#L529-L543), [context](https://github.com/can1357/oh-my-pi/blob/v18.13.2/packages/coding-agent/src/extensibility/extensions/types.ts#L680-L746)). This is the strongest extension-side tree/project identity. The task-channel payload itself has `parentToolCallId`, not `parentId`, and does not include a child working directory; if the external UI consumes only those payloads, it must not pretend that a tool-call id is a parent-agent id. Extensions are rebound into children, so an adapter that installs one bus listener per instance must deduplicate/target by `ctx.agent.id` rather than processing each shared event repeatedly.

The task channels are present in upstream source and exported from the task module, but they are not listed among the typed `pi.on` event names in the public authoring page. Treat their names/shapes as a source-verified but less stable extension seam than the documented `ExtensionAPI` methods.

### Agent Hub and RPC snapshots

Agent Hub's live registry distinguishes `running`, `idle`, `parked`, and `aborted`: a running agent has an active turn; idle has finished a turn but remains live for follow-up; parked is saved to disk; aborted is terminal until revived. It shows model role/resolved model, task/activity, current tool/arguments, retry state, and parent/child lineage ([official subagent docs](https://omp.sh/docs/subagents#what-you-see-while-workers-run), [upstream Agent Hub guide](https://github.com/can1357/oh-my-pi/blob/v18.13.2/docs/agent-hub.md#L25-L59)). This is distinct from task progress's `completed` status: completed work may still have an idle live session.

RPC supports `set_subagent_subscription` (`off`, `progress`, `events`), `get_subagents`, incremental `get_subagent_messages`, `steer_subagent`, and `cancel_subagent` ([command union](https://github.com/can1357/oh-my-pi/blob/v18.13.2/packages/coding-agent/src/modes/rpc/rpc-types.ts#L80-L87), [snapshot and frame types](https://github.com/can1357/oh-my-pi/blob/v18.13.2/packages/coding-agent/src/modes/rpc/rpc-types.ts#L394-L410), [subagent frame types](https://github.com/can1357/oh-my-pi/blob/v18.13.2/packages/coding-agent/src/modes/rpc/rpc-types.ts#L691-L707)). Forwarding defaults to off. `get_subagents` provides id/index/agent/status/task/assignment/sessionFile/progress/parentToolCallId; the progress contains current tool and resolved model. The RPC snapshot lacks an explicit `parentId` and `cwd`; for full tree identity, the Collab/Agent Hub registry snapshot is richer. RPC docs describe lifecycle/progress/events and steering/cancellation semantics ([RPC subagent subscriptions](https://github.com/can1357/oh-my-pi/blob/v18.13.2/docs/rpc.md#L1032-L1087)).

For project grouping, Collab host discovery reports session id/name, `workingDirectory`, model, PID, turn `busy`, `inputRequired`, and room access/connection metadata. Its agent registry snapshots carry `parentId` and status; task progress carries model/tool details ([Collab discovery fields](https://github.com/can1357/oh-my-pi/blob/v18.13.2/docs/collab.md#L72-L90), [wire agent snapshot](https://github.com/can1357/oh-my-pi/blob/v18.13.2/packages/wire/src/index.ts#L238-L247), [wire progress payload](https://github.com/can1357/oh-my-pi/blob/v18.13.2/packages/wire/src/index.ts#L260-L299)). Thus Collab can group hosted top-level sessions by working directory and show explicit parent-child IDs. Basic task progress alone cannot supply every child worktree path.

## What can be controlled

### A custom, preloaded extension bridge

The extension context is per-session: `pi.sendUserMessage()` prompts that session, `pi.setModel(model)` changes that session's model, and `ctx.abort()` aborts its current operation ([actions](https://github.com/can1357/oh-my-pi/blob/v18.13.2/packages/coding-agent/src/extensibility/extensions/types.ts#L1925-L1971), [context abort and identity](https://github.com/can1357/oh-my-pi/blob/v18.13.2/packages/coding-agent/src/extensibility/extensions/types.ts#L680-L746)). Child sessions rebind the imported extension factory to their own `ExtensionAPI` rather than using a parent-bound instance ([child extension rebinding](https://github.com/can1357/oh-my-pi/blob/v18.13.2/packages/coding-agent/src/sdk.ts#L703-L725), [preloaded factories](https://github.com/can1357/oh-my-pi/blob/v18.13.2/packages/coding-agent/src/sdk.ts#L731-L737)).

[INFERENCE] Consequently a custom extension can accept a local command, emit a private event on `pi.events`, and have the matching child instance (checked against `ctx.agent.id`) call its own `sendUserMessage`, `setModel`, or `abort`. This is feasible from the public extension APIs shown, but it is a source-derived design inference, not an end-to-end tested bridge, and does not require reaching into `AgentSession` internals. It is **not** a built-in control endpoint: routing, authorization, stale-id handling, result acknowledgement, and lifecycle cleanup would all be extension-owned. Do not expose generic event-bus emission to an untrusted client.

The extension must already be loaded into each target session. The authoring docs say factories initialize at session startup and require a new session after code changes; upstream loading rules say newly enabled modules not imported at startup require restart ([official authoring guide](https://omp.sh/docs/extension-authoring#load-and-test-it), [upstream extension-loading behavior](https://github.com/can1357/oh-my-pi/blob/v18.13.2/docs/extension-loading.md#L172-L176)). The same authoring guide warns that extensions have OMP's filesystem, network, environment, and process privileges and are unsandboxed ([security note](https://omp.sh/docs/extension-authoring#package-and-distribute-it)). This is not a hot-load path for sessions already running without the extension.

### Collab and RPC

Collab is the supported attach surface for an already-running TUI session that has opted in through `/collab` or `collab.autoStart`. `omp collab list --json` is metadata-only; `omp collab link <id> --view` requests a view URL, while the default link is full-control. Each hosted room publishes private IPC (a named pipe on Windows, not a TCP listener) after its relay connects; its local registry is under the OMP runtime directory ([discovery and IPC](https://github.com/can1357/oh-my-pi/blob/v18.13.2/docs/collab.md#L72-L90)). A full link can read the full transcript, prompt/interrupt, and operate Agent Hub subagents; a view link can still read live and historical transcript/tool data ([permission model](https://github.com/can1357/oh-my-pi/blob/v18.13.2/docs/collab.md#L113-L142)). A link is a bearer secret and must not be handed to a dashboard without explicit user authorization.

RPC instead starts a process with JSONL commands on stdin and events on stdout ([RPC protocol/startup](https://github.com/can1357/oh-my-pi/blob/v18.13.2/docs/rpc.md#L1-L20)). Its `set_model` changes the RPC session itself; `steer_subagent`/`cancel_subagent` address children registered under that RPC session. There is no `set_subagent_model` command in the RPC command union. Local smoke checks confirmed RPC state/subagent queries on a newly launched, owned ephemeral process only; this is not evidence of attachment to any existing interactive process ([local check](./omp-local-smoke.md)).

## Ask, approval, and human decisions

`tool_approval_requested` and `tool_approval_resolved` are useful observation events, but the `pi.on` handler signatures have no approval-result return value. `ExtensionUIContext.approve()` requests a UI decision for that extension call; it is not an API to resolve some other native pending approval ([event shape/handlers](https://github.com/can1357/oh-my-pi/blob/v18.13.2/packages/coding-agent/src/extensibility/extensions/types.ts#L1295-L1312), [approval UI contract](https://github.com/can1357/oh-my-pi/blob/v18.13.2/packages/coding-agent/src/extensibility/extensions/types.ts#L268-L346)).

For an opted-in Collab session, OMP already has the supported bridge. `ExtensionUIController.showCollabAwareApproval()` presents the approval choice list remotely as a `select` and returns the guest's selected answer; `showAskDialog()` races the local ask dialog against writable-guest responses. The Collab wire UI request types are `select` and `editor`; rich ask answers are adapted into per-question selections/custom text ([approval bridge](https://github.com/can1357/oh-my-pi/blob/v18.13.2/packages/coding-agent/src/modes/controllers/extension-ui-controller.ts#L677-L760), [ask race](https://github.com/can1357/oh-my-pi/blob/v18.13.2/packages/coding-agent/src/modes/controllers/extension-ui-controller.ts#L767-L788), [per-question guest select/editor](https://github.com/can1357/oh-my-pi/blob/v18.13.2/packages/coding-agent/src/modes/controllers/extension-ui-controller.ts#L962-L1040), [wire UI types](https://github.com/can1357/oh-my-pi/blob/v18.13.2/packages/wire/src/index.ts#L309-L326)). The first submitted/cancelled response settles the request, so any writable guest is decision-capable ([Collab guest permissions](https://github.com/can1357/oh-my-pi/blob/v18.13.2/docs/collab.md#L132-L140)). With no Collab host, these requests stay local.

For an RPC-owned process, `rpc-ui` can carry tool UI `select`/`editor` and the `ask` tool can use an explicit `ask` request after `set_ask_dialog`; the setting is off by default. RPC `extension_ui_response` answers that process's pending request. Under `--no-ui`, extension dialogs resolve to defaults; native tool approvals fail closed rather than exposing an approval UI request ([RPC ask and UI protocol](https://github.com/can1357/oh-my-pi/blob/v18.13.2/docs/rpc.md#L716-L737), [RPC UI requests/responses](https://github.com/can1357/oh-my-pi/blob/v18.13.2/docs/rpc.md#L1240-L1304)). This is still not an external control channel into a TUI process.

Attribution gap: the extension approval-resolution event reports whether approval succeeded, not which human answered. The public extension identity is agent/session identity, not human identity. The Collab UI code races local and guest answers; a dashboard can know it offered a choice, but should not claim that a particular person made it unless a separate authenticated actor record is deliberately added.

## JSONL and model-role limits

Writing session JSONL does **not** send a prompt or control command to the live in-memory agent. RPC's command transport is stdin; Collab uses authenticated live IPC. Transcript reads (`get_subagent_messages`, Hub transcript viewing) read persisted history by registered child/session file and offset; a file's existence establishes history, not a running process ([RPC command transport](https://github.com/can1357/oh-my-pi/blob/v18.13.2/docs/rpc.md#L1-L20), [Hub persisted-vs-live semantics](https://github.com/can1357/oh-my-pi/blob/v18.13.2/docs/agent-hub.md#L97-L119)). Use live registry/events for status, not transcript-file presence.

Task model selection is resolved at spawn from `task.agentModelOverrides`, agent frontmatter `model`, then the parent's active/configured model; changing a `modelRoles` mapping affects subsequent task resolutions. In the local TUI, focusing a subagent and changing its model is session-only for that child. Parent RPC `set_model` and role changes do not retroactively reroute a live child; neither RPC nor documented Collab guest controls expose an explicit per-child model setter ([task model precedence](https://github.com/can1357/oh-my-pi/blob/v18.13.2/docs/task-agent-discovery.md#L220-L234), [Agent Hub child model controls](https://github.com/can1357/oh-my-pi/blob/v18.13.2/docs/agent-hub.md#L72-L82), [host-only Collab `/model`](https://github.com/can1357/oh-my-pi/blob/v18.13.2/docs/collab.md#L144), [RPC command union](https://github.com/can1357/oh-my-pi/blob/v18.13.2/packages/coding-agent/src/modes/rpc/rpc-types.ts#L80-L100)). A preloaded extension can call `setModel` through the matched child instance as described above; updating a role mapping is not that operation.

## Minimal safe integration path

1. For current sessions, start with read-only `omp collab list --json`; only show hosted sessions, grouping by reported working directory. Current local result is empty, so there is no active Collab attach target today.
2. For a running TUI session that the user elects to expose, use its `/collab view` (read-only) or full-control Collab only with explicit consent. Default to view because even view links read transcripts and tool activity; do not silently mint or persist full-control links.
3. For future sessions requiring fine-grained local telemetry or targeted child model/prompt actions without Collab, preload one auditable extension. Publish only a narrow local named-pipe API with user-only ACL, explicit session/agent IDs, authentication, bounded payloads, and an allowlist of actions. Use `ctx.agent.id/parentId` and `ctx.cwd` for identity, and task progress for current tool/model state; redact prompts/tool args by default. Never treat generic `pi.events.emit` as authorization.
4. If the desktop launches OMP itself, use one RPC process per managed session and its documented subscriptions/commands. Do not point an RPC client at a transcript file and do not describe that process as an attached existing TUI.
